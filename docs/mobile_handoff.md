# Памятка для мобильщиков

Что нужно сделать в приложении на Kotlin Multiplatform, чтобы оно считало отжимания так же, как наш Python-эталон. Подробности в документах, ссылки на которые ниже.

## Что получаете

Всё это приходит одним архивом `pushup_mobile_v<версия>.zip`. В нём ещё лежат файлы моделей и эталон для автотестов, а в `README.md` архива есть оглавление, версии и контрольные суммы. Архив собирает ML-инженер командой `python make_mobile_package.py`.

- [Контракт данных](data_contract.md): `PoseFrame`, `PushupState`, код контракта на Kotlin и формат CSV. Это главный документ.
- [Сравнение моделей](model_choice.md): почему MediaPipe, какая модель и как подключать на iOS.
- [`pushup_logic.py`](../pushup_logic.py): эталон модуля отжиманий на Python (сигнал, сглаживание, пороги, подсказки, ошибки хвата).
- [`replay_csv.py`](../replay_csv.py): прогоняет эталон по CSV с телефона, нужен для сверки.
- Формат CSV для сверки: 66 колонок, раздел «CSV для сверки телефона и компьютера» в контракте.
- В архиве: `models/` (файлы моделей full и lite, на которых работаем мы: `.task` и извлечённые `litert/<вариант>/*.tflite`), `params.json` (пороги, окна и тексты счётчика, числа конвейера модели), `samples/` (записи с камеры в формате контракта) и `golden/` (ответы эталона по каждому кадру этих записей).

## Модуль точек на Android и iOS

Как подключить модель через LiteRT, подробно в [model_deployment.md](model_deployment.md). По умолчанию путь 1: библиотека MediaPipe Tasks (внутри неё LiteRT 2.3.0), на Android `com.google.mediapipe:tasks-vision:1.1.1`, на iOS Swift Package `MediaPipeTasksVision`. Путь 2 (LiteRT напрямую, свой конвейер на Kotlin) нужен, только если путь 1 окажется медленным даже на видеокарте или понадобится полный контроль. Числа конвейера для пути 2 лежат в `params.json` архива.

Настройки те же, что у нас на компьютере (`extract_pose.py` в репозитории ML-части, в архив он не входит):

| Настройка | Значение |
| --- | --- |
| Модель | `pose_landmarker_full.task`, лежит внутри приложения. Берите файл из `models/` архива или репозитория и сверяйте SHA-256 из его `README.md`: ссылка ниже ведёт на `latest`, и Google может обновить файл. Ссылка: <https://storage.googleapis.com/mediapipe-models/pose_landmarker/pose_landmarker_full/float16/latest/pose_landmarker_full.task> |
| Запасная модель | `pose_landmarker_lite.task` для слабых телефонов, та же ссылка с `lite` вместо `full` |
| Для пути 2 | `models/litert/full/` и `models/litert/lite/` архива: `pose_detector.tflite` и `pose_landmarks_detector.tflite`, извлечённые из `.task` |
| Режим | LIVE\_STREAM (у нас на компьютере тоже LIVE\_STREAM) |
| `numPoses` | 1 |
| `minPoseDetectionConfidence`, `minPosePresenceConfidence`, `minTrackingConfidence` | по умолчанию, 0,5 |

Из 33 точек MediaPipe оставляем 12: номера с 11 по 16 и с 23 по 28. Порядок как в таблице «12 точек и их порядок» в контракте и в `BodyPoint`.

## Правила из контракта коротко

- **Поворот.** Точки даём для кадра, где человек стоит головой вверх (это не обязательно портретный кадр). Если поворачиваете точки на 90 или 270 градусов, `imageWidth` и `imageHeight` тоже меняйте местами.
- **Зеркало.** В модель идёт незеркальный кадр. При рисовании поверх зеркального превью x заменяем на 1 − x, в `PoseFrame` ничего не зеркалим.
- **Время.** `timestampMs` из времени кадра камеры, строго растёт.
- **Пропущенные кадры.** Пока модель занята, кадры пропускаются, `PoseFrame` для них нет. Это нормально.
- **Нет человека.** Всё равно отправляем `PoseFrame` с `landmarks = null`.
- **Без обработки.** Значения MediaPipe как есть: MediaPipe сам их сглаживает, своего сглаживания и отсева не добавляем. На пути 2 сглаживание MediaPipe нужно повторить ([model_deployment.md](model_deployment.md), шаг 5).
- **Порядок.** В модуль отжиманий передаём кадры по одному и по порядку времени.

## Модуль отжиманий в `commonMain`

- Сейчас делайте заготовку и автотест точно по текущему `pushup_logic.py`: окна пока в кадрах (медиана последних 5 значений сигнала и «верх» за 150 кадров с сигналом), как в эталоне `golden/`. Удержание пропуска и отсев скачков не делайте, пока их нет в эталоне.
- Финальную версию пришлём новым архивом с новым эталоном, когда аналитик закончит эксперименты. В ней окна будут в миллисекундах по `timestampMs`, а параметры поменяются.
- Параметры живут внутри модуля отжиманий, код платформ их не трогает.

## Сверка телефона с эталоном

Сначала без телефона: автотест в `commonTest` прогоняет записи из `samples/` через Kotlin-модуль и после каждого кадра сравнивает ответ с `golden/`. Как именно, написано в `README.md` архива. Потом на телефоне:

1. В приложении нужен режим отладки: он пишет CSV в том же формате (66 колонок, те же названия и порядок, значения по таблице формата в контракте: дроби через точку) и запоминает, сколько повторов насчитал Kotlin-модуль.
2. CSV переносим на компьютер и запускаем `python replay_csv.py <файл>`.
3. Счёт `replay_csv.py` должен совпасть со счётом телефона. Если нет, расходится перенос логики.
4. Удобно, если режим отладки рядом с CSV пишет `.meta.json` со счётом телефона: тогда `replay_csv.py` покажет его рядом со своим. Пример есть в `README.md` архива.
5. Если `replay_csv.py` пишет «похоже, кадр не повёрнут вертикально», «похоже, кадр перевёрнут на 180 градусов» или «похоже, кадр зеркальный», ошибка в модуле точек: проверьте поворот и зеркало.

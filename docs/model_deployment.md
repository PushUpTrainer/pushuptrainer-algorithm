# Развёртывание модели на телефоне

Как запустить модель позы на Android и iOS в приложении на Kotlin Multiplatform так, чтобы точки совпадали с нашими CSV. Состояние на 30 октября 2026. Контракт данных: [data_contract.md](data_contract.md).

## Коротко

Есть два пути, оба на LiteRT (бывший TensorFlow Lite).

| | Путь 1: MediaPipe Tasks (по умолчанию) | Путь 2: LiteRT напрямую |
| --- | --- | --- |
| Что это | библиотека MediaPipe, внутри неё LiteRT 2.3.0 | свой код вокруг двух моделей `.tflite`, запуск через `CompiledModel` |
| Файл модели | `pose_landmarker_full.task` | `pose_detector.tflite` и `pose_landmarks_detector.tflite` из него |
| Совпадение с нашим CSV | полное: тот же конвейер, что у эталона | только если точно повторить конвейер из раздела «Путь 2» |
| Работа мобильщиков | подключить библиотеку, взять 12 точек | написать на Kotlin детектор, рамки, слежение и сглаживание |
| Видеокарта | Android и iOS (Metal) | Android и iOS (Metal) |

Берём путь 1. Путь 2 нужен, если путь 1 окажется медленным даже на видеокарте или понадобится полный контроль. В обоих путях модуль точек отдаёт один и тот же `PoseFrame`, и модуль отжиманий от выбора пути не зависит.

## Схема в KMP

- В `commonMain` обычный Kotlin `interface PoseSource` из контракта. Не `expect`/`actual`: обычный интерфейс проще, и так советует документация Kotlin.
- Android: класс на Kotlin в `androidMain`.
- iOS: класс на Swift в приложении реализует `PoseSource` (в Swift он виден как protocol), и приложение при запуске передаёт его в общий код. Так не нужны ни cinterop, ни CocoaPods, ни импорт Swift-пакетов (он пока в альфе).
- CocoaPods не используем: со 2 декабря 2026 он не принимает новые версии, поды LiteRT и MediaPipe там уже не обновляются.
- Сторонние KMP-обёртки LiteRT (KMPLiteRT, kflite) не берём: молодые, на iOS держатся на C API или замороженных подах.

### Что делает платформа

Только две вещи: готовит кадр и запускает модель.

1. Кадр в RGB, повёрнутый так, что человек головой вверх, незеркальный.
2. Две модели (`.tflite` из `.task`) лежат в assets (Android) или в bundle (iOS). `CompiledModel` и буферы создаются один раз.
3. Модели запускаются в одном отдельном потоке. Пока он занят, новые кадры пропускаем (как LIVE\_STREAM).
4. При остановке освобождаем модель (`close()`).

Всё остальное пишется один раз на Kotlin в `commonMain`, чистыми функциями. Все числа ниже взяты из MediaPipe 1.1.1 (графы `pose_detector_graph.cc`, `pose_landmarks_detector_graph.cc`, `pose_landmarker_graph.cc` и их калькуляторы). Они же лежат в `params.json` пакета, раздел `pose_pipeline`.

### Шаг 1. Детектор

Запускается только когда нет рамки с прошлого кадра: на первом кадре и после потери человека.

- Вход `[1,224,224,3]`: весь кадр вписывается в 224 на 224 с сохранением пропорций, поля чёрные, интерполяция билинейная. Пиксель `(p - 127.5) / 127.5`, то есть от -1 до 1 (поле становится -1).
- Выходы: `[1,2254,12]` (рамки и 4 точки) и `[1,2254,1]` (логиты).
- Якоря SSD: 5 слоёв, шаги 8, 16, 32, 32, 32; min\_scale 0.1484375, max\_scale 0.75; смещение 0,5; соотношение сторон 1; размер якоря фиксированный (ширина и высота 1). Слои с одинаковым шагом объединяются: 28×28×2, 14×14×2, 7×7×6, всего 2254. Порядок: слой, строка, столбец, якорь. Центр якоря `((x + 0.5) / fm_w, (y + 0.5) / fm_h)`.
- Разбор одной строки `r` выхода:

```text
cx = r[0] / 224 + ax      cy = r[1] / 224 + ay
w  = r[2] / 224           h  = r[3] / 224
точка k (0..3): x = r[4 + 2k] / 224 + ax, y = r[5 + 2k] / 224 + ay
score = sigmoid(clamp(logit, -100, 100)), берём при score >= 0.5
```

- NMS взвешенный: порог IoU 0,5. Все кандидаты с IoU больше 0,5 к лучшей рамке усредняются с весом score (и рамка, и 4 точки), score остаётся от лучшей. В старом графе MediaPipe и в порте TFJS стоит 0,3: его брать нельзя.
- Убрать поля: `x = (x - left) / (1 - left - right)`, `y = (y - top) / (1 - top - bottom)`, где поле с каждой стороны равно `(1 - короткая / длинная) / 2`.
- Выбор одной детекции. Для всех детекций после NMS, по убыванию score, строим рамки по шагу 2. Проходим их по порядку: каждая следующая рамка удаляет из списка оставленные раньше рамки, с которыми у неё IoU больше 0,5 (IoU по рамке без поворота: центр, ширина, высота в долях кадра), и встаёт в конец списка. Берём первую рамку итогового списка. Обычно это детекция с наибольшим score, но не всегда.

### Шаг 2. Рамка

По точкам детектора 0 (центр) и 1 (масштаб) в пикселях кадра:

```text
центр   = p0
сторона = 2 * |p1 - p0|, потом квадрат по длинной стороне и запас 1.25: итог 2.5 * |p1 - p0|
угол    = norm(pi / 2 - atan2(-(y1 - y0), x1 - x0)),  norm(a) = a - 2 * pi * floor((a + pi) / (2 * pi))
```

Точки детектора 2 и 3 не используются.

### Шаг 3. Модель точек

- Вход `[1,256,256,3]`: повёрнутая квадратная рамка вырезается из полного кадра билинейно. Пиксели за краем кадра повторяют крайний пиксель (REPLICATE, не чёрные). Пиксель `p / 255`, от 0 до 1. Пиксель тензора `(i, j)` соответствует точке кадра `центр + S * R(угол) * (i / 256 - 0.5, j / 256 - 0.5)`, где S сторона рамки в пикселях, ось y вниз.
- Выходы: `[1,195]` (39 точек по 5 чисел, в пикселях входа), `[1,1]` (есть ли человек, сигмоида уже в модели), `[1,256,256,1]` (маска, не нужна), `[1,64,64,39]` (логиты тепловой карты), `[1,117]` (точки в метрах, не нужны).
- Если `[1,1]` не больше 0,5 (человек есть только при значении больше 0,5): человека на кадре нет, `landmarks = null`, рамка на следующий кадр не строится.
- Разбор точки: `x = raw_x / 256`, `y = raw_y / 256`, `z = raw_z / 256`, `visibility = sigmoid(raw[3])`, `presence = sigmoid(raw[4])`.
- Уточнение по тепловой карте (до проекции, для всех 39 точек):

```text
col = int(x * 64), row = int(y * 64)   (дробная часть отбрасывается), точку вне [0, 64) пропускаем
окно 7x7 вокруг (col, row), у краёв обрезается; conf = sigmoid(heatmap)
если max(conf) >= 0.5:  x = sum(col * conf) / sum(conf) / 64,  y = sum(row * conf) / sum(conf) / 64
```

- Проекция в кадр (всё в долях ширины и высоты кадра):

```text
dx = x - 0.5, dy = y - 0.5
x' = (cos * dx - sin * dy) * roi.width  + roi.x_center
y' = (sin * dx + cos * dy) * roi.height + roi.y_center
z' = z * roi.width
```

- Точки с 0 по 32 это 33 точки позы (из них берём 12), точки 33 и 34 нужны для рамки, с 35 по 38 не нужны.

### Шаг 4. Слежение

Рамку следующего кадра строят по точкам 33 (центр) и 34 (масштаб) этого кадра: спроецированным и ещё не сглаженным. Формула как в шаге 2. Пока рамка есть, детектор не запускается.

### Шаг 5. Сглаживание

Обязательно: в режиме LIVE\_STREAM MediaPipe сглаживает точки всегда, и наши CSV уже сглажены. Без этого шага точки и счёт на телефоне разойдутся с эталоном.

- `visibility`: сначала скользящее среднее `v = 0.1 * v_new + 0.9 * v_prev`. Первое значение за всю работу берётся как есть, дальше среднее не сбрасывается никогда, даже после потери человека: когда он вернётся, `v_prev` это последнее значение до потери.
- `x`, `y`, `z`: фильтр One Euro на каждую точку и ось, в пикселях (`X = x * W`, `Y = y * H`, `Z = z * W`), потом обратно в доли:

```text
freq   = 1 / dt (dt в секундах по меткам времени кадров; до второго кадра 30)
alpha(c) = 1 / (1 + freq / (2 * pi * c))
dv     = (v - v_prev_raw) * scale * freq   (на первом кадре 0)
edv    = lpf(dv, alpha(1.0))
cutoff = 0.05 + 80 * |edv|
out    = lpf(v, alpha(cutoff))             lpf: первое значение как есть, потом a * v + (1 - a) * prev
scale  = 1 / s,  s = (roi_next.width * W + roi_next.height * H) / 2   (рамка следующего кадра из шага 4, в пикселях)
```

- Фильтры One Euro сбрасываются, если человек потерян или поменялся размер кадра (среднее `visibility` не сбрасывается). Если метка времени не больше прошлой, фильтр отдаёт значение без сглаживания. `presence` не сглаживается.
- Метки времени в миллисекундах, из того же источника, что `timestampMs` в `PoseFrame`.

### Подводные камни

- Порт BlazePose на TypeScript в `tensorflow/tfjs-models` удобен как образец кода, но в нём другие константы: NMS 0,3 и рамка по сглаженным точкам (как в старом графе MediaPipe), чёрные поля у модели точек (только в TFJS, в MediaPipe поля повторяют крайний пиксель). Заменить на значения из этого документа.
- В детекторе 38 операций DENSIFY (разреженные веса). На процессоре они работают, на видеокарте не проверено. Если детектор не пойдёт на видеокарту, пусть он работает на процессоре: он запускается редко.
- Android, targetSdk 35 и выше: с 1 февраля 2027 Google Play требует выравнивание нативных библиотек под страницы 16 КБ. Проверить готовый APK в APK Analyzer.
- Сжатие `.tflite` в assets лучше отключить (`noCompress`), чтобы файл читался без распаковки. В документации LiteRT 2.x это не описано, проверьте на сборке.

## Сверка с эталоном

1. Модуль отжиманий: автотест по `golden/` из пакета (оба пути одинаково).
2. Модуль точек: режим отладки пишет CSV по контракту, `python replay_csv.py <файл>` даёт тот же счёт и не пишет предупреждений про поворот и зеркало.
3. Путь 2: дополнительно сравнить точки пути 2 с путём 1 (отдельно проверить `visibility` на первых кадрах после возвращения человека в кадр) (MediaPipe Tasks) на одних и тех же кадрах телефона. Допуск по точкам ещё не замерен, начните с 0,01 доли кадра.
